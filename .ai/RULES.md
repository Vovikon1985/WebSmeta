## 1. Идентификация проекта
- **Название**: ExecutiveDocumentation
- **Тип**: Windows Desktop Application
- **Назначение**: Ведение исполнительной документации в строительстве
- **Ключевое отличие**: Связь сметной документации с AutoCAD и автоматизированное получение фактических объёмов из объектов AutoCAD с последующим использованием этих объёмов в исполнительной документации и XML

## 3. Хранение данных — КРИТИЧЕСКИЕ ПРАВИЛА

### 3.1 SQLite (основное рабочее хранилище)
- SQLite используется для ВСЕХ структурированных рабочих данных
- Смета может содержать сотни тысяч позиций — SQLite должен это выдерживать
- **ЗАПРЕЩЕНО** заменять SQLite JSON-файлами
- **ЗАПРЕЩЕНО** хранить всю смету одной JSON/XML строкой
- Обязательны: транзакции, индексы, foreign keys, constraints
- Обязательны миграции с версионированием БД
- Перед критическими миграциями создавать backup
- Каждый индекс должен иметь техническое обоснование

**Таблицы SQLite:**
```
Project, Estimate, EstimateSection, EstimateSubsection, EstimateItem
Drawing, AutoCADObject, Mark, Volume, Document, Act
History, Improvement, Settings
```

### 3.2 Файлы (НЕ хранить в SQLite без необходимости)
- **НЕ помещать** внутрь SQLite большие файлы: DWG, PDF, DOCX, изображения
- Файлы находятся в проектном каталоге
- SQLite хранит только метаданные: путь, имя, идентификатор, размер, дату, hash

**Структура папок проекта:**
```
Project/
├── Project.db
├── Source/
│   └── Estimate_Original.xml
├── Drawings/
│   └── *.dwg
├── Documents/
│   ├── АОСР/
│   ├── КС-2/
│   ├── КС-3/
│   ├── КС-6/
│   └── ...
├── Templates/
├── Export/
├── Backup/
├── Logs/
└── Settings/
    └── *.json
```

### 3.3 XML (импорт/экспорт/оригиналы)
- Импорт XML ГРАНД-Сметы → сохранение оригинала БЕЗ изменений
- Разбор XML → Validation → DTO → Mapping → Domain → SQLite
- Экспорт: SQLite → Domain → XML DTO → Serializer → XML → XSD validation
- **ЗАПРЕЩЕНО** выдумывать XML-схему
- **ЗАПРЕЩЕНО** создавать parser на основе предположений, если реальный XML доступен
- Если нужна XSD-схема — явно определить это и использовать предоставленную/официально доступную схему

### 3.4 JSON (конфигурация и правила)
- Используется ТОЛЬКО для: настроек, конфигурации, правил, параметров приложения
- **НЕ использовать** JSON как замену реляционной рабочей БД
- Файлы: application.json, project.json, autocad.json, volume-rules.json

- **ЗАПРЕЩЕНО** помещать всю смету одной строкой в SQLite

**Обязательная индексация:**
- EstimateId
- SectionId
- Коды сметных позиций
- Наименования

## 5. Основная бизнес-логика

### 5.1 Рабочий процесс
```
ГРАНД-Смета XML → Импорт сметы → Проект ИД → AutoCAD → 
Выбор объекта/геометрии → "Добавить метку" → 
Привязка объекта к позиции сметы → Получение/расчёт объёма → 
Сохранение связи → Фактический объём → 
Исполнительная документация → Акты/ведомости/отчёты/XML
```

### 5.2 Основная логическая связь системы
```
Проект → Сметная позиция → AutoCAD Object → Метка → Объём → Исполнительный документ
```
Эта связь должна быть центральной частью модели данных.

### 5.3 Механизм "Добавить метку" (главная функция)
```
Пользователь выбирает объект AutoCAD →
Нажимает "Добавить метку" →
Плагин получает объект →
Пользователь выбирает проект →
Пользователь выбирает позицию сметы →
Определяется объём →
Создаётся уникальная метка →
Метка размещается на чертеже →
Связь сохраняется в SQLite
```

### 5.4 Модель метки (минимальная)
```
MarkId, ProjectId, DrawingId, EstimateId, EstimateItemId
AutoCADObjectId, AutoCADHandle, ObjectType, LayerName
Quantity, Unit, Position, Text, CreatedAt, UpdatedAt
```
Конкретный набор полей определить на этапе архитектурного проектирования.

### 5.5 Графическая метка в AutoCAD
```
┌───────────────────────────┐
│ ИД-000125                 │
│ Работа: 01-01-001-01     │
│ Объём: 125.40 м³         │
└───────────────────────────┘
             │
             ▼
          объект
```
- Графическое представление должно быть отделено от бизнес-модели
- Текст и оформление метки НЕ должны быть единственным источником информации

### 5.6 Идентификация AutoCAD объектов
- **НЕЛЬЗЯ** связывать объект только по координатам
- Использовать устойчивую идентификацию:
  - ObjectId (с учетом ограничений при разных сессиях)
  - Handle
  - Database identity
  - Drawing identity
  - Тип объекта
  - Layer
  - Другие необходимые признаки
- Разработать надёжный механизм повторного поиска объекта

### 5.7 Объёмы

**Архитектура:**
- Создать отдельную абстракцию: `IVolumeProvider` или эквивалентную
- **НЕ смешивать** расчёт объёмов с WinForms
- **НЕ смешивать** расчёт объёмов с UI AutoCAD
- Архитектура должна позволять получать количество из:
  - 3D Solid
  - Площади
  - Длины
  - Количества объектов
  - Атрибутов блоков
  - Пользовательского значения
  - Других источников

**Хранение объёмов:**
```
CalculatedQuantity
ManualQuantity
FinalQuantity
QuantitySource
```
При ручной корректировке **НЕ уничтожать** исходный расчёт.

**Механизм обновления объёмов:**
```
Метка → AutoCAD Object → Повторное получение геометрии →
Расчёт → Сравнение → Изменение объёма → Сохранение
```
**НЕ уничтожать** историю изменения критических данных.

## 6. AutoCAD Plugin

### 6.1 Общие требования
- Отдельный проект
- AutoCAD **обязательно установлен** у пользователя
- Поддержка различных версий AutoCAD
- Поддержка русской и английской локализации AutoCAD

### 6.2 Изоляция от версий
- Основное приложение **НЕ должно** зависеть от конкретной версии AutoCAD
- AutoCAD Plugin должен быть изолирован
- Если разные версии AutoCAD требуют разные сборки плагина, предусмотреть:
```
AutoCAD Integration
├── Adapter
├── Version-specific implementation
└── Common contract
```
**НЕ привязывать** основное приложение к конкретной версии AutoCAD.

### 6.3 Локализация
- **НЕ использовать** русские/английские названия команд AutoCAD как основу бизнес-логики
- Предпочитать AutoCAD .NET API
- Если использование команды неизбежно — обеспечить локализационно независимый механизм

### 6.4 Функциональность плагина
- Команды AutoCAD
- Выбор объектов
- Чтение геометрии
- Чтение свойств
- Создание графической метки
- Получение Handle/ObjectId
- Передача данных основному приложению
- Обновление объектов
- **НЕ помещать** бизнес-логику проекта внутрь AutoCAD Plugin

### 6.5 Обмен данными App ↔ Plugin
- Разработать простой и надёжный механизм обмена
- На первом этапе допустимы:
  - Локальный IPC
  - Локальные файлы обмена
  - Named pipes
  - Другой бесплатный локальный механизм
- Выбрать наиболее простой и надёжный вариант
- **НЕ создавать** сетевой сервер
- Контракты обмена должны находиться в отдельном проекте: `ExecutiveDocumentation.Contracts`

## 7. DWG файлы

## 26. ГЛАВНОЕ ТРЕБОВАНИЕ

Создаваемое ПО должно быть фундаментом для реального профессионального приложения.

**Обязательные правила:**
- ✅ SQLite использовать как основное локальное рабочее хранилище
- ✅ XML использовать для импорта/экспорта и хранения оригинальной сметы
- ✅ JSON использовать для конфигурации и правил
- ✅ DWG/DOCX/PDF и другие большие файлы хранить в файловой структуре проекта, а в SQLite хранить их метаданные и связи

**Запреты:**
- ❌ НЕ усложнять систему без необходимости
- ❌ НЕ заменять SQLite JSON-файлами
- ❌ НЕ помещать всю смету в одну XML/JSON-строку
- ❌ НЕ выдумывать структуру реального XML
- ❌ НЕ выдумывать AutoCAD API
- ❌ НЕ создавать платные зависимости
- ❌ НЕ создавать GPL-зависимости без разрешения

**Процесс разработки:**
- Разрабатывать систему поэтапно
- После каждого этапа останавливаться
